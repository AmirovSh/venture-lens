# Отказоустойчивость: фактическое состояние и целевая схема

Проверено 17 ноября 2026 года. Документ описывает аудит и проект изменений; перечисленные ниже доработки не выдаются за реализованные.

## Что создано и доступно

В проекте четыре основных компонента: web, API, worker и PostgreSQL. Сейчас запущены три процесса Windows и один контейнер PostgreSQL. В Compose описаны те же четыре роли, но весь Compose-стек не развёрнут. API и worker собираются из одного Dockerfile.


Две текстовые модели — `qwen3.8-27b` и `deepseek-v4-flash` — объявлены одним аутентифицированным шлюзом. Общие адрес, API-ключ, клиентский сертификат и маршрут остаются общей точкой отказа. Отдельные контексты критика и фактчекера не являются отдельными сервисами или резервными экземплярами.

Один worker исполняет до двух заданий одновременно через потоки. Это один процесс, а не два независимых worker.

Пять локальных компонентов (web, API, worker, PostgreSQL, SearXNG) находятся на одном компьютере. Независимого резервного узла приложения нет.

При аудите:

- web: HTTP 200;
- API: HTTP 200, чтение исследований из БД успешно;
- worker: процесс присутствует; отдельного постоянного сигнала его готовности нет;
- PostgreSQL: контейнер running, постоянный том, `restart: unless-stopped`;
- SearXNG: HTTP 200, но проверочный поисковый запрос вернул **0 результатов**; движки сообщили rate limits и CAPTCHA. Это деградация зависимости, несмотря на HTTP 200.

## Что произойдёт при отказе сейчас

| Отказ | Фактическое поведение | Пробел |
|---|---|---|
| Закрытие вкладки | Worker продолжает работу, результаты читаются после открытия страницы | Это проверено на уровне отдельного серверного выполнения |
| Падение web | Анализ может продолжаться, интерфейс недоступен | Обычный процесс не перезапускается автоматически |
| Падение API | Уже взятые worker задания могут продолжиться напрямую через БД; запуск новых исследований и UI-запросы не работают | Нет автоматического перезапуска/балансировки |
| Падение worker | Сохранённые этапы остаются в БД; работа останавливается до появления исполнителя | Перезапуск процесса вручную; lease сам процесс не поднимает |
| Истечение lease задания | Действующий worker может повторно захватить задание после 120 секунд с последнего heartbeat и продолжить по сохранённым артефактам | Нужны жёсткая проверка права записи старого исполнителя и ограничение повторных захватов |
| Завершение процесса PostgreSQL | Docker может перезапустить контейнер; том остаётся | Нет standby/автопереключения; зависшие процессы и нехватка диска не устраняются политикой restart |
| Недоступность БД | API-запросы могут завершиться ошибкой; необработанная ошибка в цикле захвата может завершить worker; heartbeat тоже может прекратиться | Нет устойчивого ожидания БД и координации возобновления |
| Таймаут LLM | До трёх попыток с текущим конфигом, возможна смена модели, затем ошибка этапа/partial | Оба варианта используют общий шлюз; Retry-After/circuit breaker не реализованы |
| HTTP 401/403 LLM | Повторы прекращаются | Нет автоматического восстановления секрета/сертификата и уведомления оператора |
| Неправильный JSON LLM | Pydantic отклоняет ответ; ограниченные повторы, затем ошибка этапа | Недостаточно классификации ошибок и обратной связи для исправления схемы |
| Падение SearXNG | Часть запросов завершается ошибкой; collect может использовать исходный каталог для предварительной карточки | Кеш документов вызывается не на всех ветках ошибок; автоматической цепочки SearXNG → Exa нет |
| Пустая выдача SearXNG | Поиск по сохранённым публичным страницам; при нехватке данных — предварительная карточка | Адаптеры Exa и публичного поиска существуют как альтернативные режимы, не как полноценный failover |
| Отказ отдельного сайта | При наличии сохраняется поисковый фрагмент; данных может не хватить для допуска | Нет универсального PDF/JS-загрузчика; обход CAPTCHA не предусмотрен |
| Повреждение кеша/файла | Некоторые ошибки могут сорвать этап; исходная страница может оказаться недоступной повторно | Нужны проверка контрольных сумм, атомарная запись всех кешей и восстановление |
| Отказ Docker Desktop | PostgreSQL и SearXNG недоступны одновременно | Общая локальная зависимость |
| Отказ компьютера/диска | Весь локальный сервис недоступен; возможна потеря БД и снимков | Нет независимого хоста, резервного хранилища и проверенного восстановления актуальной БД |

Срок исследования сейчас отсчитывается от времени создания: после 45 минут длительный простой может помешать продолжению даже при сохранённых этапах. Таймер нужно отделить от времени ожидания недоступной зависимости.

Текущее выполнение — at-least-once: после неопределённого сбоя внешний LLM-запрос может повториться и быть повторно тарифицирован. Уникальный ключ задания не гарантирует единственность внешнего вызова.

## Перезапуск, пересоздание и пересборка

1. **Перезапуск процесса** — повторный запуск того же приложения. Для native web/API/worker сейчас автоматического supervisor нет. `start.ps1` работает по ручному вызову и не следит за процессами постоянно.
2. **Пересоздание контейнера** — запуск нового экземпляра из готового образа с сохранением постоянных томов. Текущая Docker restart policy сама не восстанавливает удалённый контейнер или утраченный образ.
3. **Пересборка** — создание нового образа/сборки из исходников. Есть Dockerfile, Compose и команды сборки; автоматического CI/CD, реестра версий и rollback нет.
4. **Переключение на другой узел** — продолжение обслуживания при потере хоста. Сейчас отсутствует.
5. **Восстановление данных** — возврат БД и источников из резервной копии. Том Docker сохраняет данные при перезапуске контейнера, но резервной копией не является. Начальная SQLite-копия не содержит всех актуальных данных PostgreSQL.

В Compose `restart: unless-stopped` указан для четырёх сервисов. В реально запущенном локальном окружении он действует на контейнеры PostgreSQL и существующего SearXNG. У них при проверке отсутствовал Docker healthcheck. В шаблоне Compose healthcheck предусмотрен только для БД. `/api/health` возвращает статический статус и признаки конфигурации; он не проверяет работоспособность зависимостей.

Docker документирует restart как реакцию на завершение контейнера/перезапуск движка: [restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/). `depends_on: service_healthy` управляет порядком запуска; постоянный контроль готовности и восстановление зависимостей нужно проектировать отдельно: [Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/).

## Целевая схема: первый эксплуатационный этап

Один сервер с автоматическим восстановлением процессов остаётся допустимым первым этапом, но отказ хоста всё ещё означает простой.

- Управляемый запуск web/API/worker через systemd на Linux либо полноценный supervisor/service manager при сохранении Windows/mTLS. Авторизованный серверный доступ к LLM согласуется отдельно, без копирования личного закрытого ключа.
- `/live` проверяет, что процесс работает; `/ready` — возможность обслужить запрос. Для API проверяются БД и версия схемы; недоступность LLM отражается как деградация возможностей, а не причина бесконечно перезапускать API. Отдельный endpoint/сигнал worker сообщает heartbeat, лаг очереди и доступность БД.
- Для всех процессов: ограничение частоты перезапусков, задержка, корректное завершение, лимиты CPU/RAM и внешнее наблюдение за доступностью. Сбой одного провайдера не должен вызывать массовые перезапуски здоровых компонентов.
- Worker ждёт восстановления БД с ограниченными интервалами; не теряет задания из-за завершения главного цикла. Для каждой попытки выдаётся новый fencing token. Перед записью проверяется актуальное владение заданием; старый исполнитель лишается права менять результат.
- Повторы задач: `next_retry_at`, экспоненциальная задержка с jitter, максимальное число попыток и отдельная очередь окончательно неуспешных задач. Ожидание зависимости не тратит бюджет активного выполнения исследования.
- Остановка исследования становится устойчивой к гонкам: после подтверждённой отмены поздний результат не меняет статус и не возвращает карточку в работу. Незавершённый сетевой вызов не считается автоматически отменённым у поставщика.
- LLM-адаптеры получают отдельные endpoint/секреты, индивидуальные таймауты и circuit breaker. 429 учитывает Retry-After; 401/403 и ошибки сертификата переводят зависимость в ожидание оператора. Резервная модель того же шлюза считается резервом модели, а не резервом провайдера.
- Поиск получает реальную цепочку провайдеров: SearXNG → разрешённый независимый поисковый API → кеш. При недоступности всех провайдеров исследование помечается как ограниченное источниками. Отсутствие доказательств не превращается в бизнес-отказ.
- Новые состояния интерфейса: ожидание зависимости, повтор в указанное время, выполнено с пробелами, требуется действие. Пользователь видит причину, сохранённый прогресс и доступные действия.
- Снимки источников хранятся как неизменяемые объекты по хешу. Объект записывается до ссылки на него в БД, целостность проверяется; временные файлы и старые артефакты очищаются по политике хранения.
- Резервное копирование охватывает PostgreSQL и источники. Копия хранится вне основного сервера; автоматическая проверка восстановления выполняется в отдельной БД. Для восстановления на момент времени нужны base backup и непрерывный архив WAL: [PostgreSQL PITR](https://www.postgresql.org/docs/current/continuous-archiving.html).
- Мониторинг охватывает диск, память, БД, heartbeat worker, возраст самого старого задания, ошибки и задержки провайдеров, долю неподтверждённых утверждений, бюджет, срок сертификата и возраст последней успешной резервной копии. Уведомления доставляются только по отдельно согласованному каналу.

Предлагаемые цели первого этапа (требуют проверки, не являются текущей гарантией): перезапуск упавшего процесса до 30 секунд, возврат брошенного задания до 3 минут, потеря данных при восстановлении из копий до 15 минут и восстановление сервиса до 1 часа. Конкретные RPO/RTO нужно подтвердить измерением на выбранной инфраструктуре.

## Целевая схема: отказ одного узла

Для продолжения работы при потере сервера нужны как минимум два узла приложения в разных доменах отказа и независимые контуры данных/маршрутизации:

- два узла web/API и как минимум два worker, распределённых между узлами;
- отказоустойчивый балансировщик/управляемый ingress с health probes;
- PostgreSQL с репликой и проверенным механизмом выбора лидера; предпочтительно управляемая HA-БД. Для самостоятельного автоматического failover нужен кворум, одного второго PostgreSQL недостаточно;
- независимое объектное хранилище и резервные копии вне основного контура;
- второй разрешённый LLM-провайдер с отдельным маршрутом и учётными данными;
- независимый поисковый API вместо нескольких названий движков внутри одного метапоиска.


## Управляемая пересборка и обновления

Целевая последовательность: commit → проверки контракта/тесты → сборка версионированных образов → сохранение в реестре → запуск новой версии отдельно от действующей → smoke tests → переключение трафика → наблюдение → возврат предыдущего образа при регрессии.

Перезапуск при аварии использует последний проверенный образ и не зависит от доступности Git/npm/PyPI. Пересборка выполняется конвейером доставки, а не на каждом падении процесса. Новая сборка создаётся вне каталога работающего Next.js: локальная проверка уже выявляла блокировку `.next/standalone` на Windows при попытке сборки поверх работающего приложения.

Миграции БД должны быть версионируемыми и совместимыми с предыдущей версией приложения. Автоматический откат образа не означает безопасного автоматического отката данных.

## Приёмочные сценарии перед серверным размещением

1. Завершить процесс web/API/worker в изолированном тестовом окружении: измерить restart и сохранность прогресса.
2. Разорвать соединение с БД во время heartbeat, вызова LLM и записи результата: после восстановления нет потери задания или записи старым владельцем.
3. Запустить два worker, задержать первого за срок lease: записать итог может только актуальный владелец.
4. Смоделировать 429, 503, timeout, неверный JSON, 401 и истёкший сертификат: проверить классификацию, лимиты, ожидание и переключение.
5. Отключить SearXNG и независимо его внешние движки: проверить реальную выдачу резервного провайдера и честный статус при полном отказе.
6. Отменить исследование во время внешнего запроса и затем возобновить сеть: поздний ответ не отменяет действие пользователя.
7. Заполнить ограниченный тестовый диск/повредить кеш: сервис сообщает причину и сохраняет согласованность данных.
8. Восстановить резервную копию на чистом окружении: сверить исследования, решения, ссылки и контрольные суммы источников; измерить RPO/RTO.
9. Выпустить неисправный образ и откатить его: проверить доступность, совместимость схемы и продолжение очереди.
10. Для HA-контура выключить целый тестовый узел: проверить маршрутизацию, лидерство БД и отсутствие двойной записи.

В рамках этого аудита действующие процессы и контейнеры намеренно не выключались; отказные сценарии выше пока являются планом, а не выполненными испытаниями.
