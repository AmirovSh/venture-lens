# Платформа и доставка Venture Lens

[Демонстрационный сервис](https://venture-lens.duckdns.org) работает на VPS. Доступ, компоненты и лимиты демостенда описаны в [SERVER.md](SERVER.md). Действующая цепочка доставки описана в [DELIVERY.md](DELIVERY.md).

| Слой | Демонстрация | Шаблон производственного развёртывания |
| --- | --- | --- |
| Интерфейс | Next.js | Две реплики с поэтапным обновлением |
| API | FastAPI, 1–2 реплики по CPU | 2–6 реплик по CPU |
| Исполнитель | 1–2 реплики по очереди PostgreSQL | 2–8 реплик по очереди |
| Данные и источники | PostgreSQL и SeaweedFS с постоянными томами | Внешние PostgreSQL и S3 |
| Доставка | Argo CD читает конфигурацию из GitHub | GitOps с продвижением проверенных образов |

API и worker используют один образ, отдельные процессы и проверки готовности. Только внешние сервисы или узлы в разных доменах отказа дают устойчивость к потере хоста. Сервер моделей применяет общие квоты независимо от числа worker.

## Рабочий цикл и восстановление

1. API фиксирует исследование и задание в одной PostgreSQL-транзакции. Worker забирает доступное задание через `FOR UPDATE SKIP LOCKED`, выдаёт уникальный lease и увеличивает epoch.
2. После каждого содержательного этапа сохраняются артефакт, аудит и состояние. Другой worker продолжает сохранённые этапы, не запускает весь анализ заново.
3. Каждая запись результата проверяет владельца, epoch, срок lease и поколение отмены в той же транзакции. Старый исполнитель после передачи задания не может перезаписать новый результат. Это не отменяет уже отправленный платный запрос провайдеру.
4. Heartbeat продлевает lease. При потере БД исполнитель прекращает запись; другой заберёт задание после истечения lease. Отмена исследования увеличивает поколение и немедленно лишает старые запросы права записи.
5. Недоступный LLM, поиск или S3 переводят этап в `waiting` с `next_retry_at`. Учитываются Retry-After, общий circuit breaker, общий лимит параллельных запросов и запросов в минуту. Лимит действителен для всех worker этого приложения, но не для сторонних клиентов шлюза.
6. Временные ожидания не расходуют активное время исследования; суммируется время работы его исполнителей. Повторы ограничены. После исчерпания попыток задание становится failed, исследование partial; есть ручной повтор из сохранённых артефактов.
7. SIGTERM прекращает выдачу новых этапов. Текущий ограниченный по времени запрос может закончиться; затем сохранённая работа передаётся другой реплике. Принудительное завершение покрывается lease/fencing.
8. API `/api/live` проверяет процесс; `/api/ready` — БД и нужную схему. Worker имеет собственные live/ready. Readiness убирает pod из обслуживания; liveness не перезапускает исправный процесс только из-за отказа внешнего LLM. Метрики очереди доступны на `/api/metrics`, состояние провайдеров — на `/api/dependencies`.

Kubernetes перезапускает/заменяет pod из готового образа. Argo CD восстанавливает конфигурацию из Git. **Новый образ собирается при изменении кода в CI**, а не при каждом падении процесса. Неудачное обновление не считается успешной доставкой: важны rollout, readiness и состояние Application.

Снимки источников адресуются SHA256 и проверяются при чтении. Кеш можно пересоздать; источник и результаты исследования — постоянные данные. Падение web/API не удаляет результаты и не останавливает независимые worker. Недостаток доказательств показывается как review/завершение с пробелами, а техническое ожидание — как waiting.

## Проверки

GitHub Actions запускает тесты PostgreSQL, проверку манифестов, испытания отказоустойчивости, восстановление из резервной копии, масштабирование и синхронизацию GitOps в изолированном окружении.

`fault_tests.py` ограничен собственным контекстом и namespace с меткой `local-disposable`. Он проверяет полный цикл по сетевому контракту LLM, сохранение решения и индекса 80, замену API, аварийное завершение worker/перехват lease, недоступность LLM/отложенный повтор, отключение PostgreSQL (`live=200`, `ready=503`), возврат БД с прежнего PVC, отключение/возврат S3, две реплики worker без двух завершённых результатов одного этапа.

KEDA проверяется реальным оператором: изолированная PostgreSQL-метрика вызывает **1 → 2 → 1 worker**. Это проверка механизма autoscaling, не нагрузочное измерение производительности и не масштабирование физических узлов. В production используется запрос настоящей очереди. Argo проверяется изменением безвредного environment marker: он возвращает значение из Git, Application — `Synced / Healthy`.

Результаты проверок собраны в [VERIFICATION.md](VERIFICATION.md). В автоматических испытаниях сервер моделей заменён синтетическим провайдером. Рабочее подключение проверено отдельным коротким запросом через API.

## GitHub Actions и доставка

`.github/workflows/ci.yml`: PostgreSQL-тесты → production-сборка Next.js → проверка репозитория/манифестов → изолированный Kubernetes → fault/restore/scaling/GitOps → архив именно проверенных образов. На push в main/master отдельная job с `packages:write` публикует эти образы в GHCR, без пересборки. PR не получает секреты рабочего окружения и не публикует образы.

`promote.yml` вызывается вручную с тремя digest SHA256. Создаётся release-ветка и PR с обновлением production overlay, затем явно запускается проверка этой ветки. Слияние проверенного PR меняет желаемую конфигурацию Argo. Для этой операции в настройках GitHub должны быть разрешены создание PR через Actions и запуск Actions; защиту main, обязательные checks и review настраивают после создания репозитория.

**Репозиторий опубликован в [GitHub](https://github.com/AmirovSh/venture-lens), облачные проверки запущены. Их результат и GHCR-публикация проверяются в Actions; серверный Argo CD читает GitHub напрямую.** Production overlay намеренно содержит обязательные placeholders. `platform/preflight.py` отвергает незаполненную конфигурацию, изменяемые image tags и plaintext Secret. Перед подключением production Application задайте домен, подготовьте доверенный шлюз входа и его общий ключ подписи с API. Передайте ключ через Secret `venture-lens-auth` (`AUTH_CONTEXT_SECRET`) в том же namespace. Шлюз проверяет сессию и подписывает контекст, который ожидает API. Направляйте публичные запросы через шлюз и ограничьте прямой доступ к API. Проверьте итоговые манифесты обычным preflight, а затем проверьте вход, роли и изоляцию на стенде. Production-профиль поставляется как шаблон.

## Резервное копирование

`Dockerfile.backup` использует совместимый `pg_dump` 17.12. `platform/backup.py` создаёт custom-format PostgreSQL dump, затем копирует неизменяемые `sources/` в **отдельное backup S3**, проверяя SHA256 каждого источника. Manifest завершения записывается последним; незавершённый префикс не считается пригодной копией. Кеш не копируется. Секреты libpq передаются через окружение, не аргументы процесса.

Production CronJob: каждые 6 часов, запрет пересечения, ограниченные повторы и deadline. Нужен отдельный Secret `venture-lens-backup` с `BACKUP_S3_ENDPOINT_URL`, `BACKUP_S3_REGION`, `BACKUP_S3_BUCKET`, `BACKUP_S3_ACCESS_KEY`, `BACKUP_S3_SECRET_KEY`. Bucket создаётся отдельно, с шифрованием, lifecycle/retention и желательно Object Lock. Runtime Secret предоставляет источник и PostgreSQL. В облаке предпочтительнее workload identity, а не постоянные access keys.

`backup_test.py` запускает реальный backup image, скачивает и проверяет объекты manifest, восстанавливает custom dump через `pg_restore --exit-on-error` в **новую** базу `restore_*`, проверяет сохранённые решения. Действующая БД не очищается. Тестовый бакет проверяет процедуру. Для защиты от потери сервера нужна отдельная внехостовая копия. Ориентир RPO 6 часов относится только к успешно выполняющемуся расписанию; RTO и PITR требуют серверных измерений.

Восстановление на сервере: выбрать завершённый manifest → проверить все SHA256 → восстановить источники в новый bucket → создать пустую БД и выполнить `pg_restore --exit-on-error --no-owner --no-privileges` с нужными сервисными ролями → проверить количество исследований/решения/источники → переключить новые подключения только после проверки. Инкрементальные/WAL-копии обеспечиваются HA PostgreSQL/PITR-провайдером.

## Что настраивается после выбора сервера

- Репозиторий GitHub, registry permissions, branch protection и действительный URL Argo Application.
- Для VPS системный адрес и реквизиты сервера моделей задаются оператором в `venture-lens-runtime`.
- HTTPS на DuckDNS-домене и роли owner/viewer уже настроены для публичного демо. Для нескольких независимых рабочих областей остаются OIDC и дополнительные ограничения egress загрузчика.
- Отдельные физические домены отказа: несколько worker-узлов, для HA K3s — 3 server-узла/quorum, либо управляемый Kubernetes. Один арендованный сервер с Kubernetes не переживёт отказ своего диска/хоста.
- HA PostgreSQL и S3 вне единственного узла, внехостовые резервные копии, проверка restore/PITR, дисковые лимиты и нагрузочные испытания.
- Prometheus/Grafana и доставка уведомлений: недоступность API/БД, возраст очереди, просроченные lease, блокировка провайдеров, последний успешный backup, заполнение диска. Эндпоинты и базовые probes реализованы; централизованный мониторинг с уведомлениями пока не развёрнут.

Два LLM на одном шлюзе делят квоты и доступность. Код поддерживает отдельные `LLM_FALLBACK_BASE_URL` и `LLM_FALLBACK_API_KEY`; реально независимый резервный шлюз пока не предоставлен. SearXNG может отвечать HTTP 200 с CAPTCHA/пустой выдачей; Exa требует собственного ключа. Масштабирование worker не устраняет эти ограничения и не должно превышать квоты провайдеров.
