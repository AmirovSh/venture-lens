# Venture Lens

Репозиторий с историей: [AmirovSh/venture-lens](https://github.com/AmirovSh/venture-lens) (публичный). Проверки: [GitHub Actions](https://github.com/AmirovSh/venture-lens/actions).

Сервис поиска и проверки бизнес-моделей с локальным запуском и рабочей демонстрацией на VPS. Главный результат — одинаковые по структуре карточки, открытые доказательства и сравнение моделей на горизонте первой оплаты за 90 дней.

Материалы для сдачи: [SUBMISSION.md](SUBMISSION.md). Покрытие задания: [SPEC_COMPLIANCE.md](SPEC_COMPLIANCE.md). Реальные результаты и проверки: [VERIFICATION.md](VERIFICATION.md). Готовое видео: `deliverables/venture-lens-demo.mp4` (2:50,5).

Новые возможности: итог исследования, краткая сводка запуска, задачи по доказательствам, расширенное сравнение и учёт экспериментов. При первом открытии каждого раздела появляется подсказка с затемнением вне фокуса; её можно отключить и снова вызвать кнопкой «Инструкция». Правила и хранение: [DECISION_WORKSPACE.md](DECISION_WORKSPACE.md).

Журнал с пагинацией и административная ротация ключей прежних исследований: [CONNECTION_ROTATION.md](CONNECTION_ROTATION.md).

## Публичная демонстрация


Сайт работает на VPS. Анализ выполняет отдельный сервер моделей с общими лимитами запросов. Рынок, глубина подбора, источники, выводы агентов и административные настройки описаны в [PRODUCT_CONTROLS.md](PRODUCT_CONTROLS.md). Эксплуатационная документация: [SERVER.md](SERVER.md), [PUBLIC_DEMO.md](PUBLIC_DEMO.md).

## Новая платформа: Kubernetes + GitOps

Изолированный стенд: **http://127.0.0.1:3210**. Argo CD: **http://127.0.0.1:3090**. Подключение к серверу моделей настраивается отдельно; модель и промпт каждой роли доступны администратору в сервисе. PostgreSQL и S3 стенда отделены от исходного прототипа.

Команды запуска, GitHub Actions, масштабирование, резервное копирование и фактические проверки — в [PLATFORM.md](PLATFORM.md). Синтетические исследования для испытаний явно помечены `[FAULT TEST]`; это проверка механики, а не бизнес-рекомендации.

## Локальная разработка

Интерфейс: **http://127.0.0.1:3100**. OpenAPI: http://127.0.0.1:8100/docs.

```powershell
.\start.ps1
# Остановка только процессов этого проекта:
.\stop.ps1
```

Рабочая конфигурация находится в игнорируемом `.env.local`. Секреты подключения не входят в Git и образы. Для другого совместимого HTTPS API администратор может задать адрес и ключ в разделе «Модели и промпты».

PostgreSQL проекта: контейнер `venture-lens-db`, порт **127.0.0.1:55436**, отдельный постоянный том `venture-lens-postgres`. Локальный поиск — существующий SearXNG на 127.0.0.1:8088; его настройки и контейнер сервис не изменяет. Для запуска после перезагрузки Docker должен работать; при необходимости: `docker start venture-lens-db`.

Эксплуатационные параметры подключения и проверка доступности описаны в [SERVER.md](SERVER.md).

## Установка с нуля

Требуются Python 3.11+, Node.js 22+, PowerShell. Для PostgreSQL нужен Docker или отдельный экземпляр БД.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock.txt
npm.cmd ci
Copy-Item .env.example .env.local
# Заполнить .env.local (не добавлять ключи в Git).
npm.cmd run build
.\start.ps1
```

Для независимого от Docker запуска задайте `DATABASE_URL=sqlite:///./data/venture-lens.db`. Перед запуском существующей БД выполните `.venv\Scripts\python.exe -m backend.migrate`. SQLite подходит для одного локального сервиса; PostgreSQL рекомендуется для нескольких исполнителей. Первоначальная SQLite-БД этого проекта сохранена как диагностическая копия. Скрипт `scripts/migrate_local.py` переносит её только в пустую PostgreSQL-БД, не удаляя оригинал.

## Как пользоваться

1. Создайте исследование: рынок вне СНГ, 10–15 моделей, команда и бюджет эксперимента.
2. Дождитесь поиска и анализа. Работу выполняет отдельный worker, поэтому закрытие страницы её не останавливает.
3. В обзоре различаются прошедшие модели, отказы, недостаток доказательств и технические ошибки.
4. Откройте карточку. Вкладки: обзор, паспорта утверждений, критика/фактчекинг, план эксперимента.
5. Выберите 2–3 модели флажками и нажмите «Сравнить модели».
6. Сохраните решение и заметку. Экспорт JSON содержит сохранённые результаты и снимок правил исследования.
7. «Журнал исследования → Проверить изоляцию» показывает точные входные пакеты вызовов, модель, версию промпта и хеш.

Старые диагностические исследования сохранены честно: они показывают сбои подключения и нерелевантный публичный поиск, обнаруженные при разработке. Это не успешные исследования и не демонстрационные данные.

## Конвейер

`Открытый каталог → кандидаты → поиск и снимки источников → обязательные фильтры → критик → независимый поиск фактчекера → детерминированный индекс → карточка`.

Исходные каталоги и ограничения заданы в `config/policy.yaml`. Кандидаты извлекаются из реально загруженных страниц, а не из заранее подготовленного списка. Модель может найти меньше запрошенного — фактическое количество видно в интерфейсе.

Каждый обязательный критерий имеет `pass / reject / review`. Для pass/reject сервер требует паспорт с дословной цитатой полной страницы. Цитата проверяется по сохранённому тексту. Поисковый фрагмент не позволяет пройти фильтр. Правильное цитирование не доказывает истинность или достаточность источника — интерпретация тоже требует проверки.

Модели с review не включаются в основной рейтинг. Отказы сохраняют критерии и объяснения. Для прошедших моделей аудит обязателен. В конфигурации v3.0 аудит выполняется также для предварительных карточек с review (`audit_review_models`): это помогает исследовать риски, но не допускает их в рейтинг. Подтверждённый отказ останавливает дальнейший анализ. Независимое подтверждённое противоречие пройденному обязательному условию переводит карточку в review; первичный отбор и прежние проверки сохраняются.

Критик не видит оценку отборочного этапа. Фактчекер получает только компанию, отдельные тезисы `{claim_id, statement, factual}` и результаты собственного поиска. Заголовок риска, важность, уверенность, источники и вердикт критика не передаются. Общих историй сообщений и памяти нет. Проверяется изоляция контекста, а не статистическая независимость моделей.

Модели можно назначать по ролям: `LLM_MODEL`, `LLM_DISCOVERY_MODEL`, `LLM_SCREENING_MODEL`, `LLM_CRITIC_MODEL`, `LLM_VERIFIER_MODEL`. `LLM_FALLBACK_MODEL` включает резервную модель. Каждый фактический выбор сохраняется в аудите.

## Оценка

Веса в YAML: доступ к покупателям 30%, оплата за 90 дней 25%, скорость MVP 20%, доступность эксперимента 15%, независимость запуска 10%. Каждый компонент оценивается от 0 до 5 с обоснованием и ссылками на утверждения.

`Индекс = сумма(вес × балл × 20) − штраф подтверждённого риска`.

Неизвестная оценка даёт 0 для нижней и 100×вес для верхней границы. Покрытие показывает долю весов с основаниями. Рейтинг сортируется по нижней границе, по умолчанию от слабой к перспективной. Одинаковые исходные оценки и настройки дают одинаковое число.

Штраф — наибольший подтверждённый риск: высокий 15, средний 8, низкий 3 балла; частичное подтверждение — половина. Суммирование нескольких связанных рисков не применяется, чтобы не считать одну проблему несколько раз. Неизвестный тезис и суждение не считаются подтверждённым фактом. Числовые правила также находятся в YAML. Оценка не является калиброванной вероятностью успеха.

Финансовый критерий проверяется отдельным контрактом: тип метрики, сумма USD и паспорт цитаты. Сервер сопоставляет сумму с денежным значением в цитате и требует контекст оценки/сделки/капитализации. Это консервативная проверка: сложные форматы записи могут дать review, но инвестиции и выручка не принимаются за оценку. Неподтверждённая сумма не выводится как установленный масштаб аналога.

## Надёжность

- Задания и этапы сохраняются в БД. PostgreSQL использует `FOR UPDATE SKIP LOCKED`; SQLite — условный захват задания.
- Lease и heartbeat позволяют вернуть незавершённое задание после падения исполнителя.
- Завершённые артефакты переиспользуются при повторе; запрос внешнему провайдеру после неопределённого сбоя может повториться и тарифицироваться повторно.
- Запись модели и постановка её задания выполняются одной транзакцией. Ключ задания уникален.
- Таймауты и число повторов ограничены, ошибки отображаются в журнале. HTTP 401/403 не повторяются бесконечно.
- Токены включают фактическое usage и консервативный резерв для незавершённых/неопределённых вызовов. Это не счёт в долларах.
- Источники сохраняются в `data/sources`, кеш полных страниц действует сутки и сохраняет исходную дату получения.
- Поиск кешируется на сутки. При ограничении движков используется поиск по ранее загруженным публичным документам. При отсутствии новых страниц предварительная карточка может опираться только на исходный каталог — это отмечается в журнале и не означает прохождение фильтров.
- Фактчекер самостоятельно формирует короткие нейтральные поисковые запросы, отделяя проверяемый факт от прогнозной части тезиса.
- Несовпадающие свидетельства не удаляются. Для нерешённого противоречия используется review/unknown.

## Проверки

```powershell
npm.cmd run typecheck
npm.cmd run build
.\.venv\Scripts\python.exe -m pytest -q
```

Для тестов PostgreSQL задайте переменную `TEST_DATABASE_URL`. Каждый тест создаёт отдельную временную схему и удаляет только её. Данные приложения не очищаются. На PostgreSQL дополнительно проверяется, что заблокированное задание пропускается другим исполнителем.

Проверки охватывают сохранённый результат всего конвейера с подменённым провайдером, контракт LLM-запроса и аудит, изоляцию пакетов, выдуманную цитату, поисковый фрагмент, короткое замыкание отказа, отмену, lease, повтор, решение пользователя, экспорт и SSRF. Реальный LLM-прогон выполняется отдельно; тестовые фикстуры не подмешиваются в рабочие исследования.

Для повторной проверки завершённого исследования есть `scripts/recheck.py RUN_ID`: готовые досье и критика сохраняются, предыдущая проверка переносится в историю. По умолчанию заново выполняется поиск фактчекера; `--reuse-sources` использует сохранённые страницы, `--model-id ID` ограничивает перепроверку одной карточкой. Скрипт разрешает повтор только неактивного исследования без выполняющихся заданий и изменяет поколение/epoch. Выполняйте его в административном окружении с доступом к БД.
