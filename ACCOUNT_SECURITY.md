# Пароли и административное восстановление

В кабинете есть «Настройки аккаунта»: текущий пароль, новый пароль (12–128 символов), подтверждение. После сохранения завершаются все сессии аккаунта, отзываются незавершённые ссылки восстановления; исследования продолжают работу. Новый пароль хранится только как PBKDF2-SHA256, 600 000 итераций.

## Владелец и администраторы



## Забытый пароль

1. На странице входа нажать «Забыли пароль?», ввести логин, способ связи и необязательное сообщение.
2. Ответ одинаков для существующего и неизвестного аккаунта. Ссылка или временный пароль в ответ не выдаются. Повторная заявка не заменяет контакт в уже открытом запросе.
3. Любой администратор открывает общую очередь. Контакт и сообщение из заявки **не подтверждают владение аккаунтом**: нужно проверить личность по ранее известному каналу или иным надёжным сведениям. В интерфейсе требуется явное подтверждение этой проверки.
4. После ввода своего текущего пароля администратор получает одноразовую ссылку на 15 минут. Он передаёт её человеку по проверенному каналу вручную. Почтовые и мессенджерные отправки не подключены.
5. Пользователь открывает ссылку и самостоятельно задаёт новый пароль. Администратор его не видит. Старые сессии завершаются, использованная ссылка больше не работает.

Администратор может отклонить заявку или перевыпустить ссылку: предыдущая сразу становится недействительной. При одновременной обработке проверяется версия заявки; устаревшее действие возвращает 409 и требует обновить список. Ссылка показывается администратору только при выпуске. Её токен находится в URL-фрагменте, удаляется из адресной строки JavaScript и передаётся серверу только в POST. В БД сохраняется SHA256 токена, а не ссылка.

Заявки ограничены тремя попытками на IP и логин в час. Операции безопасности — десятью попытками на IP/аккаунт за 15 минут. Критические изменения сериализованы блокировками строк PostgreSQL; потребление токена и смена пароля происходят в одной транзакции. Сохраняется журнал `account_security_events`: кто изменил роль, выдал/отклонил восстановление, сменил пароль или завершил сброс. Паролей и токенов в журнале нет.

## Аварийный доступ владельца


```powershell
.\.venv\Scripts\python.exe platform\configure_public_demo.py --rotate-owner
@'
k3s kubectl -n venture-lens-demo rollout restart deployment/demo-access
k3s kubectl -n venture-lens-demo rollout status deployment/demo-access --timeout=120s
'@ | .\.venv\Scripts\python.exe platform\ssh_client.py
```

Новый пароль появляется только в приватном файле владельца; гостевой пароль не меняется. Новый bootstrap-хеш отменяет прежний пароль владельца и его сессии, включая пароль, установленный через кабинет. Команду не нужно выполнять при обычном обновлении приложения.

## Развёртывание и проверка

Миграция `0004_account_security` добавляет роли, заявки, переопределение пароля владельца и журнал. После миграции `configure_public_demo.py` выдаёт gateway SELECT/INSERT и UPDATE только `password_hash`/`role` для аккаунтов, доступ к служебным таблицам и INSERT в журнал. Доступа к исследованиям у роли gateway нет.

`ACCOUNT_SECURITY_ENABLED` в публичном ConfigMap включает операции и ссылку восстановления. При первом выпуске сначала обновлены все API/auth-реплики с выключенным флагом, затем флаг включён. Выключение флага не возвращает старые пароли: проверка переопределений владельца работает независимо от него. После смены паролей нельзя откатывать gateway на старую версию, игнорирующую таблицу `account_security`.

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe platform\verify_account_security.py
```

Внешняя проверка использует только два QA-аккаунта из `.platform/registration-check-accounts.json`: временно назначает второго администратором, меняет пароль первого, проходит восстановление, проверяет одноразовость и завершение сессий, затем возвращает административную роль к прежнему значению. Новые QA-пароли сохраняются в том же приватном файле. Проверка не запускает исследования, не меняет пароль владельца и не печатает реквизиты или ссылки.
