# Закрытая демонстрация на VPS

Проверено 18 ноября 2026 года. VPS `91.108.213.165`: Ubuntu 24.04, 4 vCPU, 8 ГБ RAM, 60 ГБ NVMe. Сервис работает в K3s, namespace `venture-lens-demo`. По выбранному пользователем сценарию домен и публичный ingress пока не настроены.

## Доступ

- Приложение: **http://127.0.0.1:3210**.
- Эти адреса доступны на данном компьютере через SSH. Сайт на публичном IP сервера не публикуется.

После перезапуска компьютера:

```powershell
.\.venv\Scripts\python.exe platform\start_demo.py
```

Нужен существующий SOCKS-шлюз `127.0.0.1:18080`; его настройки не изменялись. Скрипт запускает mTLS-адаптер и SSH-туннель в фоне. Журналы: `.platform/demo-tunnel.*.log`, PID: `.platform/demo-tunnel.pid`. Туннель автоматически переподключается при обрыве SSH. Локальный K3d-стенд использует те же порты 3210/3090: одновременно запускать его с VPS-туннелем нельзя.


## Платформа

| Компонент | Конфигурация демо |
| --- | --- |
| Next.js web | 1 реплика |
| FastAPI API | HPA, 1–2 реплики по CPU |
| Python worker | KEDA, 1–2 реплики по готовой очереди PostgreSQL |
| PostgreSQL 17.12 | 1 StatefulSet, постоянный том |
| SeaweedFS S3 4.54 | 1 StatefulSet, постоянный том; источники по SHA256 |
| SearXNG | 1 реплика, image закреплён digest, внутренняя сеть |
| K3s | v1.37.2+k3s1, systemd, шифрование Secrets включено |
| Argo CD / KEDA | v3.6.1 / v2.21.1 |

Шесть компонентов приложения — web, API, worker, PostgreSQL, S3 и поиск — имеют отдельные контейнеры. Дополнительно работают контроллеры платформы. Это **один физический домен отказа**: отказ VPS/диска остановит всё размещённое на нём. Реплики на одном сервере не обеспечивают HA хоста.

API и worker используют общие лимиты провайдеров в PostgreSQL. Увеличение числа worker не отменяет квоты LLM и поиска. Ошибки зависимостей переводят работу в ожидание с повторами; потерянный worker освобождается через lease и fencing. Probes и Kubernetes пересоздают контейнеры. Argo CD восстанавливает объявленную конфигурацию из Git. При дефектном образе нужен возврат к проверенному релизу; автоматической генерации исправлений кода нет.

## GitOps и CI/CD


GitHub Actions с проверками, fault-тестами, публикацией проверенных образов в GHCR и продвижением digest подготовлены в `.github/workflows`. **GitHub-репозиторий ещё не подключён, облачные Actions не запускались.** Для автоматических релизов нужно подключить репозиторий/registry, защиту ветки и переключить источник Argo CD. Production overlay содержит обязательные placeholders и не используется как готовая конфигурация.

Bootstrap: `platform/server/bootstrap.sh` → `build.sh` → `deploy.py` → `addons.py`. До запуска нужны проверенный SSH-ключ, исходники `/opt/venture-lens/source`, приватный `runtime.json` и Secret настроек SearXNG. `addons.py` использует официальные manifests версий из `platform/toolchain.json`, сохранённые на VPS как `keda-install.yaml` и `argocd-install.yaml`. Секреты исключены из Git bundle и Docker context.

## Резервное копирование

Создать новую копию, скачать на компьютер, проверить SHA256 и пробное восстановление:

```powershell
.\.venv\Scripts\python.exe platform\backup_demo.py --verify-restore
```

`pg_dump` создаёт согласованный дамп; неизменяемые источники копируются после него. Кеш для восстановления не нужен. Копия на самом VPS не защищает от потери VPS; внехостовая копия — скачанная папка на компьютере. **Регулярное внешнее расписание пока не включено.** Production CronJob для отдельного backup S3 подготовлен; доступ к хранилищу ещё не задан. Гарантированного RPO/PITR на демо нет.

При аварии восстановить дамп в новую пустую БД, источники в новый bucket, проверить manifest/SHA256, записи и заметки, затем переключить подключения. Скрипт пробного восстановления не меняет подключение рабочего приложения.

## Администрирование


Снаружи firewall разрешает только SSH 22/tcp; pod/service сети разрешены для внутренних соединений. Kubernetes API закрыт firewall. Web/Argo port-forward слушают только loopback, HTTP передаётся внутри зашифрованного SSH. Перед публичной демонстрацией нужны домен, TLS и авторизация; пока 80/443 открывать не нужно.

Проверка через существующий маршрут:

```powershell
@'
k3s kubectl -n venture-lens-demo get pods,hpa,scaledobject
k3s kubectl -n argocd get application venture-lens
systemctl is-active k3s venture-lens-web-forward venture-lens-argo-forward venture-lens-llm-relay
'@ | .\.venv\Scripts\python.exe platform\ssh_client.py
```

`venture-lens-web-forward`, `venture-lens-argo-forward`, `venture-lens-git`, `venture-lens-llm-relay` включены в systemd, имеют `Restart=always` и следуют перезапуску K3s. Для доступа без этого компьютера нужен собственный безопасный SSH-маршрут и защищённая копия ключа.

Для длительного использования остаются автономный доступ к LLM, GitHub/registry, домен/TLS/авторизация, внешние регулярные backups и мониторинг с уведомлениями. Для устойчивости к отказу хоста нужны несколько узлов и внешние/HA сервисы данных. Нагрузочная ёмкость этого VPS пока не измерялась.
